# Code Generation

## Overview

R65 compiles to WLA-DX assembly format for the 65816 processor. The code generator transforms MIR (Mid-level Intermediate Representation) into readable, debuggable assembly that matches hand-written patterns.

**Design Principles**:
- **Readable Output**: Clear labels, comments, and structured sections
- **Deterministic**: Same source → same assembly every time
- **Debuggable**: Source locations and metadata at function headers
- **Explicit Control**: Programmer specifies register usage; compiler is a translator, not an optimizer
- **Predictable**: Match hand-written assembly patterns
- **WLA-DX Native**: Follow assembler conventions

**Pipeline**:
```
MIRProgram → Memory Allocation → Register Allocation → Instruction Selection →
Addressing Mode Selection → Assembly Emission → WLA-DX Assembly (.asm)
```

## Memory Allocation

### Overview

The MemoryAllocator tracks and allocates memory locations for static variables, ensuring no conflicts and optimal placement.

### Storage Classes

**Zero-Page (Direct Page)** - Fastest access ($00-$FF)
- Explicit: `#[zeropage(0x20)]`
- Auto-allocated: `#[zeropage]` (finds next free byte)
- Size: 256 bytes total
- Access time: 2-3 cycles

**RAM** - SNES Work RAM ($7E0000-$7FFFFF)
- Explicit: `#[ram(0x7E0000)]`
- Auto-allocated: `#[ram]` (finds next free range)
- Size: Up to 128KB
- Access time: 4-5 cycles

**Hardware Registers** - Memory-mapped I/O
- Explicit: `#[hw(0x2100)]` (required)
- Volatile access (every read/write hits hardware)

**ROM** - Read-only data
- Explicit: `#[rom(0x8000)]`
- Stored in ROM banks

### Allocation Strategy

1. **Process explicit allocations first** - reserves specific addresses
2. **Process auto-allocations second** - finds free spots
3. **Conflict detection** - prevents overlapping allocations

### Type Sizes

- `u8, i8, bool` → 1 byte
- `u16, i16` → 2 bytes
- Near pointers (`*T`) → 2 bytes
- Far pointers (`far *T`) → 3 bytes
- Arrays → `element_size * length`
- Structs → sum of field sizes (packed)

### Generated Symbol Definitions

**Constants**:
```asm
.EQU TILE_SIZE 8
.EQU BUFFER_SIZE 256
```

**Variables**:
```asm
.DEFINE TEMP $0020              ; Zero-page
.DEFINE INIDISP $2100           ; Hardware register
.DEFINE BUFFER $7E0000          ; RAM
```

## Register Allocation

### Philosophy

R65's register allocation is **NOT** an optimizing allocator. It follows these principles:

1. **Explicit Control**: Programmer specifies register usage via register aliasing
2. **Predictable Output**: Same source always generates same assembly
3. **Minimal Automation**: Compiler uses designated scratch space only
4. **Trust the Programmer**: No clever heuristics or interference

The compiler is a **translator**, not an optimizer.

### Virtual Registers

MIR uses unlimited virtual registers (`%0, %1, %2, ...`) during lowering. These must be mapped to physical locations for code generation.

### Allocation Priority

1. **Hardware Registers** (A, X, Y) - handled by MIR register aliasing
2. **Memory Locations** - explicit `#[zeropage]`, `#[ram]` attributes
3. **Scratch Registers** - designated zero-page locations
4. **Stack** - last resort when scratch exhausted

### Physical Locations

Virtual registers map to:

**Hardware Registers**: `A`, `X`, `Y`
```asm
LDA #$42        ; %0 allocated to A
```

**Scratch Registers**: Designated zero-page ($16-$1F typical)
```asm
LDA #$42
STA $16         ; %0 allocated to scratch $16
```

**Stack Slots**: `[SP+offset]`
```asm
LDA #$42
PHA             ; %0 allocated to stack
```

**Memory**: Direct references
```asm
LDA #$42
STA TEMP        ; %0 allocated to memory location TEMP
```

### Scratch Register Pool

Scratch registers are designated zero-page locations:
```rust
#[zeropage(0x16, register)]
static mut SCRATCH0: u8;

#[zeropage(0x18, register)]
static mut SCRATCH2: u16;  // Takes 0x18-0x19
```

Features:
- Track available scratch locations
- Allocate to virtual registers
- Free and reuse when registers die
- Size-aware allocation (1-byte vs 2-byte)

## Instruction Selection

### Overview

The InstructionSelector converts MIR instructions into 65816 assembly mnemonics using WLA-DX syntax.

**Input**: MIR instructions (Load, Store, BinaryOp, etc.)
**Output**: 65816 assembly (LDA, STA, ADC, etc.)

### Instruction Mapping

#### Memory Operations

**Move (Assignment)**:
```
MIR: dest = source

8-bit:
    LDA #$2A        ; Load immediate
    STA $16         ; Store to scratch

16-bit:
    LDA #$34        ; Low byte
    STA $16
    LDA #$12        ; High byte
    STA $17
```

**Load** - `dest = *source`:
```asm
LDA BUFFER      ; Load from memory
STA $16
```

**Store** - `*dest = source`:
```asm
LDA $16
STA BUFFER      ; Store to memory
```

#### Arithmetic Operations

**Add**:
```
MIR: dest = a + b

Generated:
    LDA a_loc
    CLC
    ADC b_loc
    STA dest_loc
```

**Subtract**:
```
MIR: dest = a - b

Generated:
    LDA a_loc
    SEC
    SBC b_loc
    STA dest_loc
```

**Multiply (power of 2)**:
```
MIR: dest = a * 8

Generated:
    LDA a_loc
    ASL A           ; Shift left 1
    ASL A           ; Shift left 2
    ASL A           ; Shift left 3
    STA dest_loc
```

**Multiply (general)** - calls runtime function:
```
MIR: dest = mul(a, b)

Generated:
    LDA a_loc
    LDX b_loc
    JSR __mul_u8
    STA dest_loc
```

#### Bitwise Operations

**AND**:
```asm
LDA a_loc
AND b_loc
STA dest_loc
```

**OR**:
```asm
LDA a_loc
ORA b_loc
STA dest_loc
```

**XOR**:
```asm
LDA a_loc
EOR b_loc
STA dest_loc
```

**NOT**:
```asm
LDA a_loc
EOR #$FF        ; Flip all bits
STA dest_loc
```

#### Control Flow

**Branch**:
```
MIR: branch_if cond, target_label

Generated:
    LDA cond_loc
    BEQ target_label    ; Branch if false
    ; fall through
```

**Jump**:
```
MIR: jump target_label

Generated:
    JMP target_label
```

**Function Call**:
```
MIR: call function_name

Generated:
    JSR function_name    ; Near call
    JSL function_name    ; Far call (for far fn)
```

**Return**:
```
MIR: return [value]

Generated:
    [optional: load return value into A]
    RTS              ; Near return
    RTL              ; Far return (for far fn)
```

## Addressing Modes

### Overview

The AddressingModeSelector chooses the optimal addressing mode based on operand type, address range, and instruction requirements - prioritizing smaller code size and faster execution.

### 65816 Addressing Modes

| Mode | Example | Size | Cycles* | Use Case |
|------|---------|------|---------|----------|
| Immediate | `LDA #$42` | 2 bytes | 2 | Constants |
| Accumulator | `INC A` | 1 byte | 2 | A register ops |
| Direct Page | `LDA $20` | 2 bytes | 3 | Zero-page ($00-$FF) |
| Absolute | `LDA $2000` | 3 bytes | 4 | Standard memory |
| Long | `LDA $7E0000` | 4 bytes | 5 | 24-bit addresses |
| Direct Page,X | `LDA $20,X` | 2 bytes | 4 | Zero-page arrays |
| Absolute,X | `LDA $2000,X` | 3 bytes | 4-5** | Standard arrays |
| Absolute,Y | `LDA $2000,Y` | 3 bytes | 4-5** | Standard arrays |
| Indirect | `LDA ($42)` | 2 bytes | 5 | Pointers |
| Indirect,Y | `LDA ($42),Y` | 2 bytes | 5-6** | Pointer arrays |
| Long,X | `LDA $7E0000,X` | 4 bytes | 5 | Large arrays |

\* Approximate cycles (varies with processor mode)
\*\* +1 cycle on page boundary crossing

### Selection Logic

1. Check if hardware register (accumulator mode)
2. Get effective address from location
3. Determine address range:
   - `$00-$FF` → Direct Page
   - `$100-$FFFF` → Absolute
   - `>$FFFF` → Long
4. Apply modifiers (indexing, indirection)
5. Return mode and formatted operand

### Examples

**Direct Page Selection** (address $20):
```asm
LDA $20         ; Direct page (fastest)
```

**Absolute Selection** (address $2000):
```asm
LDA $2000       ; Absolute
```

**Long Selection** (address $7E0000):
```asm
LDA $7E0000     ; Long addressing
```

**Indexed** (with X register):
```asm
LDA $20,X       ; Direct page indexed
LDA $2000,X     ; Absolute indexed
```

**Indirect** (through zero-page pointer):
```asm
LDA ($42)       ; Indirect through $42
LDA ($42),Y     ; Indirect indexed
```

## Function Generation

### Overview

The FunctionCodeGenerator orchestrates all components to generate complete, commented function bodies with headers, labels, and control flow.

### Function Header Format

```asm
; ============================================================================
; Function: process_player
; Source: game.r65:42
; Preserves: X, Y
; Parameters: player_id @ A: u8
; Returns: health @ A: u8
; ============================================================================
process_player:
    ; Function body...
    RTS
```

### Generation Pipeline

1. **Setup register allocator** for this function
2. **Allocate all virtual registers** in function
3. **Create instruction selector**
4. **Emit function header** comment with metadata
5. **Emit function label**
6. **Order basic blocks** for optimal control flow
7. **Generate basic blocks**:
   - Emit block label (except entry block)
   - Emit instructions in block
8. **Blank line** after function

### Basic Block Ordering

**Linearization Strategy**:
- Entry block first
- Breadth-first traversal for natural control flow
- Minimize jumps where possible

### Example Generated Function

```asm
; ============================================================================
; Function: calculate_damage
; Source: combat.r65:15
; ============================================================================
calculate_damage:
    ; Load attack value
    LDA ATTACK
    STA $16         ; Store to scratch

    ; Load defense value
    LDA DEFENSE
    STA $17

    ; Calculate: damage = attack - defense
    LDA $16
    SEC
    SBC $17
    STA DAMAGE

    ; Return damage in A
    LDA DAMAGE
    RTS

```

## Complete Assembly Generation

### Overview

The ProgramCodeGenerator is the top-level coordinator that generates complete WLA-DX assembly files from MIR programs, integrating all components.

### Complete Generation Pipeline

```python
1. Create AssemblyEmitter
2. Emit file header and processor directives
3. Emit memory map
4. Memory allocation (allocate all statics)
5. Symbol definitions (emit constants and variables)
6. Function code generation:
   - Organize functions by bank
   - Emit bank directives
   - Generate function code for each bank
7. Interrupt vector table
8. Write output file (or return as string)
```

### Bank Organization

Functions are organized by bank boundaries:
```asm
; ============================================================================
; Bank 0 - Main Code
; ============================================================================
.BANK 0 SLOT 0
.ORG 0

main:
    ; ...

init_hardware:
    ; ...

; ============================================================================
; Bank 1 - Graphics Code
; ============================================================================
.BANK 1 SLOT 0
.ORG 0

decompress_graphics:
    ; ...
```

### Interrupt Vector Table

Generated using WLA-DX SNES vector directives:
```asm
; ============================================================================
; Interrupt Vectors (Native Mode)
; ============================================================================
.SNESNATIVEVECTOR
COP __empty_handler
BRK __empty_handler
ABORT __empty_handler
NMI nmi_handler
IRQ irq_handler
.ENDNATIVEVECTOR

; ============================================================================
; Interrupt Vectors (Emulation Mode)
; ============================================================================
.SNESEMUVECTOR
COP __empty_handler
ABORT __empty_handler
NMI __empty_handler
RESET reset_handler
IRQBRK __empty_handler
.ENDEMUVECTOR
```

Unused vectors point to `__empty_handler` (a stub that just executes `RTI`).

## Static Initialization

### Overview

The compiler automatically generates an `__init_start()` function for all static variables with explicit initializers. This is critical because **SNES RAM is NOT zeroed on power-on** - contents are unpredictable.

### Generation Rules

1. **Variables with initializers are included** - Even `= 0` initializers are included
2. **Variables without initializers are excluded** - They have undefined values
3. **Entry point integration** - `#[entry]` functions automatically call `__init_start()`

### Example

**Source code**:
```rust
#[zeropage(0x20)]
static mut FLAGS: u8 = 0x80;     // Initialized (non-zero)

#[zeropage(0x21)]
static mut COUNTER: u8 = 0;      // Initialized (zero) - MUST initialize!

#[ram]
static mut TEMP: u8;             // Uninitialized - undefined value!

#[entry]
fn main() -> ! {
    TEMP = 0;  // Must initialize manually
    loop { }
}
```

**Generated `__init_start()`**:
```asm
__init_start:
    LDA #$80
    STA FLAGS           ; FLAGS = 0x80
    STZ COUNTER         ; COUNTER = 0 (must initialize even if zero!)
    RTS
```

**Generated `main()`**:
```asm
main:
    JSR __init_start    ; Initialize all statics first
    ; ... rest of main
```

### Edge Cases

| Scenario | Behavior |
|----------|----------|
| No explicit initializers | `__init_start()` not generated |
| Zero initializers | Included (RAM not zeroed on SNES) |
| Complex expressions | Evaluated and stored |
| Multiple entry points | Each calls `__init_start()` |

### Design Rationale

- **Hardware accuracy**: SNES RAM has unpredictable contents at power-on
- **Explicit over implicit**: Only variables with `= value` are initialized
- **Automatic integration**: Programmer doesn't need to remember to call init

| Component | Responsibility | Input | Output |
|-----------|---------------|-------|--------|
| **MemoryAllocator** | Allocate static variables to memory locations | Static declarations | Address mappings |

## Design Trade-offs

**Readability vs Size**:
- Prioritize readable output over minimal code size
- Use clear labels and comments
- Structured sections make debugging easier

**Determinism vs Optimization**:
- Same source always produces same assembly
- No clever heuristics that might change behavior
- Predictability over optimization

**Explicitness vs Automation**:
- Programmer controls register allocation via aliasing
- Compiler uses minimal scratch space
- Trust programmer intent

**Performance Strategy**:
- Use fastest addressing modes where possible (direct page)
- Avoid unnecessary moves
- Generate straightforward instruction sequences
- Let WLA-DX assembler handle final optimization
